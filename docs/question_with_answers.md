12分＋質疑3分という前提で、**教授から突っ込まれやすいポイント**を重要度順に整理します。想定質問と「どう答えるとよいか」も併記します。

**📌マーク**は本システムのソースコード・ドキュメントから引用した回答です。

## ① 新規性・既存研究との差分（最重要）
**突っ込まれやすい質問**
- 「既存の自動バグ修正研究と何が本質的に違うの？」
- 「LLMを使っている点以外の新規性は？」

**答え方の軸**
- RPCスキーマ"差分"に着目し、**変更理由（互換性・移行・意味変更）を暗黙的に含む入力**を使っている点
- 既存研究では困難だった**修正理由の説明可能性**を志向している点  
→ まとめスライドの主張を明確に言語化する [1]

**📌 本システムからの補足回答（設計より）**
> 本研究は **gRPC / Protocol Buffers** のスキーマ差分（diff）を入力として、Automated Program Repair（APR）手法で自動的に修正パッチを生成することを目的としています。差分情報だけで修復候補を提示できれば、実験再現性・トレーサビリティが向上する。
> *(出典: [design_jp.md](design_jp.md))*

## ② 精度34.7%の評価の妥当性
**突っ込まれやすい質問**
- 「34.7%は低くない？」
- 「"開発者が参考にできる"とは具体的にどう判断した？」

**答え方の軸**
- 完全自動修正ではなく**"開発支援ツール"**としての位置づけ
- 「人間が参考にできるレベル」= **修正の方向性・影響箇所の特定**ができること
- 部分的でも正しい方向を示せば、人間の作業時間を大幅短縮できる
- GitHub Copilotも100%の精度ではなく、**人間との協調**が前提  
→ 「完璧な自動化」ではなく「効果的な支援」を目指す実用的アプローチ [1]

### 🎯 「人間が参考にできる」の定義

本研究における「参考にできる」とは、以下のいずれかを満たすことを指します：

| レベル | 内容 | 人間の作業量削減効果 |
|--------|------|----------------------|
| **完全一致** | そのまま適用可能 | 100%削減（手作業ゼロ） |
| **意味的等価** | 軽微な調整で適用可能 | 90%削減（微調整のみ） |
| **部分的修正** | 正しい方向性を示している | 50-70%削減（出発点として有効） |
| **方向性の提示** | 影響箇所の特定ができている | 30-50%削減（調査時間短縮） |

**重要な視点**：
- スキーマ変更の影響範囲調査は、大規模コードベースでは**数時間〜数日**かかる
- システムが「この3つのファイルを修正すべき」と示すだけでも**大きな価値**がある
- 部分的に正しいパッチは「修正のテンプレート」として機能する

### 📌 本システムの評価基準（4軸評価システム）

本システムでは以下の**4つの独立した評価軸**でパッチを評価しています：

| 評価軸 | 内容 | 「参考にできる」への貢献 |
|--------|------|-------------------------|
| **Accuracy（正確性）** | Ground Truthと生成パッチの意味的等価性 | パッチの完成度を測定 |
| **Decision Soundness（判断の健全性）** | No-opやDeferredの判断が適切か | 誤った修正による時間浪費を防止 |
| **Directional Consistency（方向性の一貫性）** | 修正の方向性がGround Truthと一致 | **最も重要**：間違った方向に進まない |
| **Validity（実装の妥当性）** | 構文、型、依存関係の正しさ | ビルドエラーを起こさない |

**Accuracyラベル定義（5段階）**：
| ラベル | 説明 | スコア換算 | 人間が使えるか？ |
|--------|------|------------|-----------------|
| `IDENTICAL` | 意味的に同一（R0-R15ルール適用） | 1.0 | ✅ そのまま適用 |
| `SEMANTICALLY_EQUIVALENT` | 同じゴール、軽微な差異あり | 0.85 | ✅ 微調整で適用 |
| `PARTIALLY_CORRECT` | 部分的に正しい、人間が改良可能 | 0.5 | ✅ **出発点として有効** |
| `WRONG_APPROACH` | 間違ったアプローチ、書き直しが必要 | 0.25 | ⚠️ 参考程度 |
| `NO_MATCH` | 一致なし | 0.0 | ❌ 使えない |

### 💡 PARTIALLY_CORRECT（0.5点）の実用価値

**評価基準の明確な定義**：
> 「人間の開発者がこのパッチを出発点として使い、正しい解決策に到達できるか？」
> - **PARTIALLY_CORRECT** = 「改良すれば救える」← **これが研究の中核的価値**
> - **WRONG_APPROACH** = 「最初からやり直し」
> *(出典: patchEvaluation/prompt/00_evaluationPrompt.txt)*

**PARTIALLY_CORRECTの具体例**：
- ✅ 修正すべきファイルと関数を正しく特定している
- ✅ 修正の方向性（追加/削除/変更）が正しい
- ⚠️ エッジケースの処理が不足
- ⚠️ テストファイルの更新が漏れている

**なぜこれで十分か**：
1. **影響範囲の特定**：数百ファイルから修正対象を絞り込み済み
2. **修正パターンの提示**：同じ変更を他の箇所にも適用可能
3. **テストは機械的**：テスト/モックの更新は派生作業として後から追加可能

**実測データの解釈**：
- 34.7%が完全一致〜意味的等価
- さらにPARTIALLY_CORRECTを含めると **60-70%が「参考になる」レベル**
- これは「ゼロから調査する」より圧倒的に効率的

## ③ 失敗要因分析は十分か？
**突っ込まれやすい質問**
- 「なぜここまで精度が頭打ちなのか？」
- 「LLMの限界？設計の問題？」

**答え方の軸**
- 以下の3点を具体例つきで説明できると強い  
  - スキーマ差分と**変更意図の乖離**
  - **複数ファイル・複数レイヤー**にまたがる修正計画が立てられない
  - **gRPC固有のドメイン知識不足**  
→ 自己批判ができている点は高評価されやすい [1]

**📌 本システムの評価から判明した失敗パターン**

### 失敗の全体像
修士論文の実験結果より、49件の評価完了ケースのうち：
- **CORRECT（正解）**: 9件（18.4%）
- **PLAUSIBLE（妥当だが異なる）**: 8件（16.3%）
- **INCORRECT（不正確）**: 32件（65.3%）

### 🔍 4つの典型的な失敗パターン（論文より）

#### パターン1：条件分岐の単純化
**具体例**：protoから`precert`フィールドが削除され、代わりに`SubmissionType kind`で種別を判断する変更
- **人間の実装**：`kind`が`unknown`の場合に従来の`precert`で**フォールバック**（後方互換性維持）
- **LLMの実装**：「`precert`が削除された→使用しない」と単純化し、フォールバック分岐を削除
- **根本原因**：スキーマ変更の**形式は理解したが、意図（後方互換性）を把握できなかった**

```go
// 人間の実装
kind := req.Kind
if kind == pubpb.SubmissionType_unknown {
    if req.Precert {  // ← フォールバック処理
        kind = pubpb.SubmissionType_sct
    } else {
        kind = pubpb.SubmissionType_final
    }
}

// LLMの実装（誤り）
kind := req.Kind
if kind == pubpb.SubmissionType_unknown {
    kind = pubpb.SubmissionType_final  // ← フォールバック欠落
}
```

#### パターン2：多段階修正の不完全性
**具体例**：新フィールド追加に対して**ハードコード値を挿入**するだけ
- **LLMの対応**：最も直接的な変更箇所のみを修正
- **欠落した作業**：関数シグネチャ変更、呼び出し元の修正、上位・下位レイヤーの連鎖的修正
- **評価ログ**：「patch only inserts hard-coded value, missing coordinated updates」
- **根本原因**：システム全体の整合性を維持する多層的修正の本質を理解できない

#### パターン3：型のセマンティクス誤解
**具体例**：protoで`int64`型のタイムスタンプフィールド定義
- **LLMの理解**：protoの`int64`フィールドを追加（**構文は認識**）
- **必要な実装**：Go側では`*time.Time`型での扱いが必要（**意味を誤解**）
- **結果**：型変換関数（`ChallengeToPB`, `PBToChallenge`）での適切な処理が欠落
- **根本原因**：gRPCスタブとビジネスロジック間の型変換規約を理解していない

#### パターン4：修正対象ファイルの誤特定
**具体例**：proto変更の影響を受けるファイルを誤認識
- **LLMの判断**：提供コンテキスト内のファイルを分析し「このファイルが影響を受ける」と判断
- **実際**：当該protoメッセージを使用していない関数や、既に別箇所で処理済みの部分を修正
- **評価ログ**：「modified unrelated locations, did not apply required changes」
- **根本原因**：proto定義とソースコード間の依存関係グラフを正確に構築できない

### 🎯 失敗パターンの共通要因（論文結論）

| 要因 | 詳細 | 影響 |
|------|------|------|
| **1. 形式と意図の乖離** | スキーマ変更の**構文的差分**は認識できるが、その**背景や目的**（後方互換性、段階的移行、セマンティクス変更）を推論できない | パターン1の失敗 |
| **2. 局所最適化への傾向** | 提示コンテキスト内で完結する「最小限の修正」を選好し、**システム全体の整合性**を考慮した修正計画を立案できない | パターン2の失敗 |
| **3. ドメイン知識の欠如** | gRPCにおけるproto定義とスタブコードの関係、型変換規約、エラーハンドリングパターンといった**ドメイン固有知識**が不足 | パターン3, 4の失敗 |

### 💡 意図充足度（Intent Fulfillment）評価との対応
| ラベル | 説明 | 失敗パターンとの関係 |
|--------|------|----------------------|
| `INTENT_FULFILLED` | 意図を完全に満たした | 成功ケース（34.7%） |
| `INTENT_PARTIALLY_FULFILLED` | 部分的に意図を満たした | パターン2（多段階修正の一部のみ実装） |
| `INTENT_ACKNOWLEDGED_BUT_NOT_FULFILLED` | 意図を理解したが実装しなかった | パターン4（誤った箇所を修正） |
| `INTENT_NOT_FULFILLED` | 意図を誤解または無視した | パターン1, 3（意図・セマンティクス誤解） |

**評価で除外されるファイル（評価の公正性のため）**：
- `*.pb.go`, `*_pb2.py` など自動生成ファイル → protoc等で生成されるため
- `*_test.go`, `*Test.java` などテストファイル → 派生的な変更は機械的に追加可能
- `*.proto` ファイル → APRエージェントは**protoを入力として受け取り、下流コードを修正する**設計

> *(出典: docs/before/master/05_考察.tex, patchEvaluation/prompt/00_evaluationPrompt.txt)*

## ④ なぜRPC / gRPCに限定したのか？

## ⑦ LLM依存性・再現性
**突っ込まれやすい質問**
- 「モデルが変わったら結果も変わるのでは？」
- 「再現性はどう担保する？」

- 現状は**手法提案＋可能性検証**が主目的

**📌 再現性担保のための設計**

1. **プロンプトテンプレートの固定化**
   - `/patchEvaluation/prompt/00_evaluationPrompt.txt` - 4軸評価プロンプト
   - `/patchEvaluation/prompt/01_intentFulfillmentPrompt.txt` - 意図充足度評価

## ⑧ 実用化するなら何が足りない？
**突っ込まれやすい質問**
- 「実際の開発現場で使うには？」
- 「次にやるなら何？」

**答え方の軸**
- 変更意図推論の明示的モデリング
- ドメイン知識（gRPC規約）の組み込み
- マルチファイル修正計画の導入  
→ 失敗要因ときれいに対応づける [1]

**📌 評価システムが示唆する改善点**

**現状の評価で判明した課題と対応策**：
| 課題 | 評価軸での現れ方 | 改善案 |
|------|------------------|--------|
| **Proto変更を修正しようとする** | Decision Soundness: UNSOUND | エージェントへの指示強化（protoは入力コンテキスト、出力対象外） |
| **テスト・モック更新の欠落** | Accuracy: PARTIALLY_CORRECT止まり | テスト/モック更新を機械的に追加する後処理ステップ |
| **複数ファイル間の整合性不足** | Repair Types: `PARTIAL_REPAIR` | マルチステージ修復計画（`MULTI_STAGE_REPAIR`）の導入 |

**将来拡張で導入予定のRepair Types**：
- `SCHEMA_EVOLUTION`: データスキーマ変更への対応
- `INTERFACE_ADAPTATION`: API/インターフェース境界変更への適応
- `SERIALIZATION_UPDATE`: シリアライズ/デシリアライズロジックの更新
> *(出典: patchEvaluation/prompt/00_evaluationPrompt.txt)*

3. 「完璧な自動化」ではなく「GitHub Copilot型の支援ツール」として位置づけ

**想定される効果的な回答例**：
